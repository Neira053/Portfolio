Overview

What it is

Vigil answers questions over a sample engineering handbook (deployment, incident response, coding standards, on-call, security policy). The point is the engineering around the model call: caching, retries, guardrails, rate limiting, cost tracking and per-stage tracing, with an eval harness to measure retrieval instead of guessing.

A terminal-style dashboard shows request volume, latency, cache hit rate, token and cost estimates, error rate, retrieval recall and a per-stage waterfall for the latest request.

What the eval showed

Recall@5 is about 79% on a 14-query labeled set: 11 answerable questions, including paraphrases, and 3 out of scope. The misses are mostly synonym gaps, for example "text-message-verify" against "SMS-based MFA", which TF-IDF cannot bridge. One out-of-scope question ("parental leave policy") still returns a false positive.

Problem I fixed

A bug the tests caught

Failed LLM calls were being cached, so one bad response kept being served. I fixed it so errors are never cached and added a regression test that fails if it comes back.

Why it is built this way

Design choices

  • No model downloads: TF-IDF runs fully offline.
  • Mock mode by default, so every other stage still runs without an API key.
  • A minimum similarity threshold drops weak matches before reranking.
  • Cache falls back to memory when Redis is not running.
Honest limits

Known limits and next steps

  • No streaming and no multi-turn memory yet.
  • The reranker's benefit is asserted, not measured.
  • Next: real embeddings and a vector database, a cross-encoder with a before and after comparison, CI that runs pytest and the eval on every PR.
